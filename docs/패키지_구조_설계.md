### 패키지 구조 선택 이유

- 도메인 중심으로 묶으면 `user` 도메인 전체를 한 폴더에서 파악할 수 있어 유지보수성이 높다.
- 레이어 중심 구조(`controller/`, `service/`, `repository/` 최상단)는 도메인이 많아질수록 파일이 분산되어 탐색 비용이 커진다.
- `infra/`는 도메인 로직이 아닌 기술 인프라(Security, WebSocket)를 분리해 도메인과 인프라의 경계를 명확히 한다.

### DTO 구조 원칙

- `auth`, `user`, `bid`: DTO 종류가 적으므로 도메인당 파일 하나로 통합 (`AuthDto`, `UserDto`, `BidDto`)
- `auction`: 기능 범위가 넓어 파일이 길어지므로 기능 단위로 분리 (`AuctionDto`, `AuctionImageDto`, `AuctionResultDto`)
- 사용 시 `AuthDto.SignUpRequest`, `AuthDto.LoginResponse` 형태로 참조

## 2. BaseEntity 설계

### 도메인 엔티티용 — `BaseEntity`

상태가 변하고 소프트 삭제가 의미 있는 테이블에 적용한다.

**적용 대상**: `users`, `seller_profiles`, `business_profiles`, `business_members`, `auctions`, `auction_images`

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;

    private Instant deletedAt;

    public void softDelete() {
        this.deletedAt = Instant.now();
    }

    public boolean isDeleted() {
        return this.deletedAt != null;
    }
}
```

### 로그형 테이블용 — `BaseLogEntity`

한번 INSERT 후 수정/삭제가 없는 불변 이력 테이블에 적용한다.

**적용 대상**: `bids`, `auction_results`, `refresh_tokens`

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseLogEntity {

    @CreatedDate
    @Column(updatable = false)
    private Instant createdAt;
}
```

### `@EnableJpaAuditing` 설정 위치

```java
// PickzApplication.java 또는 별도 JpaConfig.java
@EnableJpaAuditing
```

### 소프트 삭제 조회 처리 방식

- `@SQLRestriction("deleted_at IS NULL")`을 각 엔티티에 적용해 기본 조회에서 삭제된 데이터를 자동으로 제외한다.
- 삭제된 데이터까지 조회가 필요한 경우(관리자, 감사 등)는 `@SQLRestriction`을 무시하는 네이티브 쿼리 또는 별도 Repository 메서드를 사용한다.

```java
// 적용 예시
@Entity
@SQLRestriction("deleted_at IS NULL")
public class User extends BaseEntity { ... }
```

## 3. JPA 연관관계 매핑 원칙

- 기본은 **단방향**으로 시작한다. 양방향이 필요한 경우에만 추가한다.
- FetchType 기본값은 **LAZY**로 설정한다. 성능 이슈 확인 후 필요한 곳만 EAGER 또는 fetch join으로 처리한다.
- Cascade는 **명시적으로 필요한 경우에만** 사용한다. 기본적으로 적용하지 않는다.

### 연관관계 방향 정리

| 관계 | 방향 | 이유 |
|---|---|---|
| `User` → `SellerProfile` | 단방향 (`@OneToOne`) | SellerProfile에서 User 탐색 불필요 |
| `BusinessProfile` → `BusinessMember` | 단방향 (`@OneToMany`) | 멤버 목록 조회는 BusinessProfile 기준 |
| `Auction` → `AuctionImage` | 단방향 (`@OneToMany`) | 이미지는 경매 기준으로만 조회 |
| `Auction` → `AuctionResult` | 단방향 (`@OneToOne`) | 결과는 경매 기준으로만 조회 |

## 변경 이력

### 2026-05-29 최초 작성

- 배경: 도메인 설계 문서만으로는 다른 개발자(또는 AI)가 일관된 구현을 하기 어렵다는 판단 하에 패키지 구조와 BaseEntity 설계를 명문화함
- BaseEntity / BaseLogEntity 분리 원칙 확정
- 소프트 삭제 구현 방식 (`@SQLRestriction`) 확정
- JPA 연관관계 기본 원칙 확정 (단방향 우선, LAZY 기본)

### 2026-05-29 DTO 구조 원칙 추가

- 배경: DTO 파일이 기능마다 늘어나면 패키지가 어지러워진다는 판단 하에 도메인별 DTO 통합 원칙을 확정함
- `auth`, `user`, `bid` → 도메인당 파일 하나로 통합
- `auction` → 기능 단위로 분리 (경매/이미지/결과)
- 패키지 트리 구조에 `dto/`, `exception/` 폴더 추가 반영
